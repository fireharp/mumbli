# Release Signing & Provenance

Every Mumbli release DMG is built by [`.github/workflows/release-please.yml`](https://github.com/fireharp/mumbli/blob/main/.github/workflows/release-please.yml). The `build-dmg` job signs the app, notarizes the DMG with Apple, and publishes signed [SLSA build provenance](https://slsa.dev/spec/v1.2/build-provenance).

## Two signing modes

The workflow picks its mode from whether the `MACOS_CERTIFICATE` secret is set.

| | Ad-hoc (fallback) | Developer ID (configured) |
|---|---|---|
| Requires secrets | No | Yes |
| Valid code signature | Yes | Yes |
| Stable cdhash across rebuilds of the same commit | Yes | Yes |
| Notarized / Gatekeeper-clean | No | Yes |
| `TeamIdentifier` in the signature | No (`not set`) | Yes |
| Accessibility permission survives updates | No — see [Accessibility Permissions](/for-developers/accessibility-permissions) | Yes |
| Usage-proof receipts work | Yes | Yes |

The fallback exists so a release never fails just because signing secrets are missing. It still produces a real code signature, which is what the usage-proof module needs in order to enroll — before this, releases were built with `CODE_SIGNING_ALLOWED=NO` and the proof module could never enroll on a released build at all.

Ad-hoc releases still show the "Mumbli can't be opened because Apple cannot check it for malicious software" dialog, and users must clear the quarantine attribute manually (`install.sh` does this).

## Setting it up

```bash
scripts/release/setup-signing-secrets.sh
```

Run it yourself — it handles your signing certificate and your App Store Connect key, and neither should pass through anything but your own shell. It checks that the `.p12` really holds a **Developer ID Application** identity with its private key, verifies the notarization credentials against Apple with `notarytool history`, generates `KEYCHAIN_PWD` itself, and only then sets the six secrets. `MACOS_CERTIFICATE` is set last, since the workflow reads its presence as "use Developer ID mode" — so a failure partway through can't leave the next release trying to notarize with credentials that never arrived. A bad value fails here in seconds instead of ten minutes into a release that already has a tag.

Any value can be supplied up front, and only the rest is prompted for:

```bash
P12_PATH=~/Downloads/Certificates.p12 P12_PASSWORD='…' \
ASC_KEY_PATH=~/Downloads/AuthKey_XXXXXXXXXX.p8 \
ASC_KEY_ID=XXXXXXXXXX ASC_ISSUER_ID=<uuid> \
  scripts/release/setup-signing-secrets.sh
```

`ASC_KEY_PATH` / `ASC_KEY_ID` / `ASC_ISSUER_ID` are the same names `build-signed-dmg.sh` reads, so one exported set drives both.

The values it needs, and where each comes from, are below.

## Required GitHub secrets

The script sets these. To do it by hand instead, add them under **Settings → Secrets and variables → Actions**.

### Signing certificate

You need a **Developer ID Application** certificate — not "Apple Development", which cannot notarize. Create it at [developer.apple.com/account/resources/certificates](https://developer.apple.com/account/resources/certificates), download it, and let it install into your login keychain. Then export it from Keychain Access (right-click the certificate → Export → `.p12`, set a password).

```bash
base64 -i Certificates.p12 | pbcopy
```

| Secret | Value |
|---|---|
| `MACOS_CERTIFICATE` | The base64 blob above |
| `MACOS_CERTIFICATE_PWD` | The password you set when exporting the `.p12` |
| `KEYCHAIN_PWD` | Any random string — it only protects the throwaway CI keychain |

### Notarization credentials

Notarization uses an App Store Connect API key, which does not expire on password rotation and needs no 2FA. Create one at [appstoreconnect.apple.com/access/integrations/api](https://appstoreconnect.apple.com/access/integrations/api) with the **Developer** role. You can download the `.p8` file exactly once.

```bash
base64 -i AuthKey_XXXXXXXXXX.p8 | pbcopy
```

| Secret | Value |
|---|---|
| `APPLE_API_KEY` | The base64 blob above |
| `APPLE_API_KEY_ID` | The key ID, e.g. `XXXXXXXXXX` (also in the `.p8` filename) |
| `APPLE_API_ISSUER` | The Issuer ID (UUID) shown above the key list |

## Testing it before a release

```bash
ASC_KEY_PATH=~/path/AuthKey_XXXXXXXXXX.p8 \
ASC_KEY_ID=XXXXXXXXXX \
ASC_ISSUER_ID=<uuid> \
  scripts/release/build-signed-dmg.sh
```

This runs the same sequence as CI — archive, sign with hardened runtime, DMG, notarize, staple, assess — on your own machine, and ends with the `spctl` verdict. Notarization is the only step that needs Apple to agree, and a release is a bad place to discover it doesn't. Omit the credentials and it still builds and signs, then reports `Unnotarized Developer ID`, which is the expected rejection for a signed-but-not-notarized DMG.

Two things this deliberately does not reproduce: release-please's tagging, and the provenance attestation (only GitHub can sign that).

The script uses the checked-in `MumbliApp.xcodeproj` rather than running `xcodegen`. XcodeGen 2.45 writes `objectVersion = 77`, which needs Xcode 16+ to open, while the checked-in project is `56`. CI's `macos-latest` runner is new enough that its `xcodegen generate` step is fine; an Xcode 15 machine is not. Pass `REGENERATE=1` to run `xcodegen` anyway.

## Where the version comes from

`MARKETING_VERSION` in `project.yml` is the single release version, and release-please bumps it. The checked-in `MumbliApp.xcodeproj` carries its own copy of that setting, which only changes when someone runs `xcodegen` — that copy is why the About pane sat at `0.3.3` while the project said `0.5.0`. release-please now bumps both (the pbxproj lines are annotated `/* x-release-please-version */`), and a `Stamp version` build phase runs `scripts/version-stamp.sh`, which reads `project.yml` and overwrites the built `Info.plist`. Whatever the Xcode project believes, the app shows the real thing.

The same script adds the commit, since a dev build is normally several commits past the last tag:

| Info.plist key | Example | Meaning |
|---|---|---|
| `CFBundleShortVersionString` | `0.5.0` | Release version, always plain semver |
| `CFBundleVersion` | `83` | `git rev-list --count HEAD` |
| `MumbliVersionDisplay` | `0.5.0+7.g1a2b3c4.dirty` | One-line build identity |
| `MumbliGitCommit` | `1a2b3c4` | Commit built from |
| `MumbliGitDescribe` | `v0.5.0-7-g1a2b3c4` | `git describe --tags --always --dirty` |
| `MumbliCommitsSinceTag` | `7` | Distance from the `v$MARKETING_VERSION` tag |
| `MumbliSourceState` | `clean` / `dirty` | Working tree at build time |

Settings > About shows the release version, plus a **Build** row with the commit that is hidden on a release build (exactly on the tag, clean tree) and copyable everywhere else. `AppVersion` in `MumbliApp/Core/AppVersion.swift` reads these, and the launch log line records `MumbliVersionDisplay`.

To see what a build here would stamp:

```bash
scripts/version-stamp.sh --print
```

Because the phase is scheduled after Xcode writes `Info.plist`, it sometimes lands after Xcode's own code-signing step; it re-signs the bundle (same identity and entitlements) when that happens. Release builds pass `CODE_SIGNING_ALLOWED=NO` and are signed later by the script above, so the stamp is already in place before any signature exists. CI checks out the release tag with full history, which is what makes `git describe` resolve to the tag exactly.

## Build provenance

After the DMG is stapled, the workflow computes `checksums.txt` and calls `actions/attest-build-provenance`, which signs a provenance statement via Sigstore binding the DMG's SHA-256 to the source commit, workflow, and runner.

Anyone can verify a downloaded DMG:

```bash
gh attestation verify Mumbli-0.5.0.dmg --repo fireharp/mumbli
```

This proves the DMG was produced by this workflow from a specific commit. It does not by itself say anything about usage receipts — that link is the release binding, described in [the usage proof docs](https://github.com/fireharp/mumbli/blob/main/docs/proof/README.md).

Digest ordering matters: `stapler staple` rewrites the DMG, so checksums and attestation are computed **after** stapling. A DMG downloaded from the release therefore matches the attested digest byte for byte.

### SLSA level, honestly

This is **Build L2**: provenance is generated and signed by a hosted build platform, and it is unforgeable by the workflow's own steps. It is not L3, because the build steps and the attestation run in the same user-defined workflow rather than an isolated, trusted build definition. Reaching L3 would mean adopting [slsa-github-generator](https://github.com/slsa-framework/slsa-github-generator)'s generic generator, which requires passing subject digests to a separate reusable workflow and verifying with `slsa-verifier` instead of `gh attestation verify`. That is a deliberate future step, not a current claim.

## Switching an existing install to Developer ID

The first Developer ID release changes the app's code signature identity. macOS TCC keys Accessibility permission to the signing identity, so **existing users must re-grant Accessibility permission once** on that update. After that, the permission becomes stable across all future updates — which is the opposite of the ad-hoc situation, where it breaks on every single build.

Mention this in the release notes for the first signed release.
